Archon MCP is primarily a developer tool designed to run close to your filesystem so it can watch code and documentation, interact with local editors, and spawn local processes. Its Dockerfile in your repo shows it is built from a Node image with a single health‑check port and is meant to run as a server

screenshot

; however, running it in a container in development introduces several problems:


File‑watching and hot reload – Archon watches your local repo for new docs/tasks. Docker binds mount host files, but in‑container file‑watchers often miss events on Windows/WSL (especially with chokidar or fs.watch). As a result, changes to your repo may not be detected in real time.


Tool integration – Many Archon tools (e.g. code-analyzer, yarn/npm tasks) shell out to local binaries. In dev mode these expect to find your local Node installation and repo dependencies. In a container you have to duplicate volumes and dependencies, which defeats the convenience of running Archon alongside your editor.


GPU and network dependencies – Archon can call other MCP servers (e.g. your local Ollama or GPU LLMs) using hostnames and ports. In Docker Desktop the host.docker.internal mapping works, but you lose cross‑container introspection. Running Archon directly on the orchestrator machine avoids that complexity.


For production or a non‑interactive orchestrator, containerization is desirable: it isolates dependencies, ensures consistent versions, and simplifies deployment. The recommended pattern is therefore:


Dev: run Archon natively (or in WSL) alongside your codebase and editor, and mount volumes for memory persistence.


Prod: build a Docker image (as in infra/docker/archon/Dockerfile.archon) and run with a persistent volume for .archon and .claude directories. Use environment variables to point it at other MCP servers (Claude Flow, MetaMCP, etc.) for orchestration.


2. Memory architecture & how to deploy it

2.1 Tiered memory design (recommended)


The “Swapping CF memory back‑ends” document describes a tiered memory strategy

screenshot

:


Tier	Purpose	Recommended backend	Notes

Tier 1: Hot cache	real‑time pub/sub, transient context	Redis	Run as a container ( docker run -p 6379:6379 redis )

screenshot

.

Tier 2: Working memory	agent state & OS context	LettaAI	Keep stateful memory of tasks; run the Letta server on orchestrator or in a container.

Tier 3: Personalization	user preferences & persona memory	Mem0 or OpenMemory	Mem0 API is simple; OpenMemory is fully local. Deploy whichever you prefer (both can run in Docker).

Tier 4: Semantic archival	long‑term vector store & code patterns	RuVector (preferred) or Qdrant	The docs recommend RuVector as the high‑performance distributed store

screenshot

; keep Qdrant as a backup if needed.

Tier 5: Knowledge graph	relationships & metadata	Graphiti + Neo4j/FalkorDB	For relational queries; run Neo4j or FalkorDB container and let Graphiti connect

screenshot

.


You can still enable AgentDB as a local fallback and to maintain compatibility with existing tools

screenshot

. The recommended arrangement is:


AgentDB: acts as the default memory adapter; enable its QUIC sync so other machines stay consistent (set AGENTDB_QUIC_SYNC=true and list peer addresses).


LettaAI: enable it (LETTA_ENABLED=true) and point LETTA_API_URL to your Letta server.


OpenMemory/Mem0: set OPENMEMORY_ENABLED=true and MEM0_ENABLED=true; both can run as microservices in Docker.


RuVector: set RUVECTOR_ENABLED=true, RUVECTOR_URL to the service address and configure consensus peers for distributed mode

screenshot

.


Graphiti: set GRAPHITI_ENABLED=true and GRAPHITI_BACKEND=falkordb to use FalkorDB; alternatively set GRAPHITI_BACKEND=neo4j and configure GRAPHITI_URI, GRAPHITI_USER, GRAPHITI_PASSWORD.


Qdrant: keep QDRANT_ENABLED=true but treat it as a backup (data can be replicated from RuVector).


Memorytensors/memOS: these are not databases but libraries for working with memory embeddings. You don’t “run” them; import them in your agents or build small CLI wrappers. They can live in your agent code or be turned into MCP tools.


2.2 Deployment choices


Containers for persistence – Run Redis, Qdrant, Neo4j/FalkorDB, and OpenMemory in Docker; mount volumes for data directories. The orchestrator PC (WSL or Linux) can run LettaAI and RuVector natively or in containers as well.


Local vs. cloud – For production or cross‑device sync, use the Supabase integration. Enable FLOW_NEXUS_ENABLED=true and set SUPABASE_URL and keys. The integration will sync your AgentDB data into Supabase tables automatically

screenshot

.


AgentDB QUIC sync – To share memory across your 4 PCs, set AGENTDB_QUIC_SYNC=true and list peer addresses in AGENTDB_QUIC_PEERS (e.g., 192.168.1.101:4433,192.168.1.102:4433). This uses the QUIC protocol for sub‑millisecond synchronization.

- **3000-3999**: Web UIs (Grafana 3000, Gitea 3000, Dify 3002, Archon 3737)

- **9000-9999**: Monitoring (Prometheus 9090, Node Exporter 9100, DCGM 9400)

- **11000-11999**: Ollama (11434)

- **12000-12999**: System services (MetaMCP 12008)

1. Choose port from reserved range

2. Add to relevant docker-compose.yml

3. Update PORT-MAPPING-REFERENCE.md (this file)

4. Create Infisical path entry: `/machines/{pc}/SERVICE_PORT`

5. Create Cloudflare route if external access needed

6. Update Tailscale ACL if specific network rules needed

Archon MCP is primarily a developer tool designed to run close to your filesystem so it can watch code and documentation, interact with local editors, and spawn local processes. Its Dockerfile in your repo shows it is built from a Node image with a single health‑check port and is meant to run as a server

screenshot

; however, running it in a container in development introduces several problems:


File‑watching and hot reload – Archon watches your local repo for new docs/tasks. Docker binds mount host files, but in‑container file‑watchers often miss events on Windows/WSL (especially with chokidar or fs.watch). As a result, changes to your repo may not be detected in real time.


Tool integration – Many Archon tools (e.g. code-analyzer, yarn/npm tasks) shell out to local binaries. In dev mode these expect to find your local Node installation and repo dependencies. In a container you have to duplicate volumes and dependencies, which defeats the convenience of running Archon alongside your editor.


GPU and network dependencies – Archon can call other MCP servers (e.g. your local Ollama or GPU LLMs) using hostnames and ports. In Docker Desktop the host.docker.internal mapping works, but you lose cross‑container introspection. Running Archon directly on the orchestrator machine avoids that complexity.


For production or a non‑interactive orchestrator, containerization is desirable: it isolates dependencies, ensures consistent versions, and simplifies deployment. The recommended pattern is therefore:


Dev: run Archon natively (or in WSL) alongside your codebase and editor, and mount volumes for memory persistence.


Prod: build a Docker image (as in infra/docker/archon/Dockerfile.archon) and run with a persistent volume for .archon and .claude directories. Use environment variables to point it at other MCP servers (Claude Flow, MetaMCP, etc.) for orchestration.

Executive Summary
Project-Nyra is a decentralized, hybrid edge-cloud AI orchestration platform designed specifically for mortgage origination and full-stack development automation. II. The Edge Plane (Local LAN)

The Orchestrator: A lightweight Minisforum PC acts as the cognitive traffic cop. All public traffic is proxied through Cloudflare Tunnels to either the Oracle Cloud apps or the Orchestrator's secured UIs via Cloudflare Access.
