infra/worker-rtx5090/start_vllm.sh ✅ (this is the real “fix”)
#!/usr/bin/env bash
set -euo pipefail

MODEL_NAME="${MODEL_NAME:-Qwen/Qwen3-4B}"
PORT="${VLLM_PORT:-8000}"
GPU_MEMORY_UTIL="${GPU_MEMORY_UTIL:-0.85}"
MAX_MODEL_LEN="${MAX_MODEL_LEN:-32768}"

# LMCache: vLLM integration via kv-transfer-config
# kv_role=kv_both means cache reads+writes
KV_TRANSFER_CONFIG='{"kv_connector":"LMCacheConnectorV1","kv_role":"kv_both"}'

echo "[vLLM] model=${MODEL_NAME} port=${PORT} gpu_mem_util=${GPU_MEMORY_UTIL} max_len=${MAX_MODEL_LEN}"
echo "[LMCache] kv_transfer_config=${KV_TRANSFER_CONFIG}"

exec vllm serve "${MODEL_NAME}" \
  --host 0.0.0.0 \
  --port "${PORT}" \
  --tensor-parallel-size 1 \
  --gpu-memory-utilization "${GPU_MEMORY_UTIL}" \
  --max-model-len "${MAX_MODEL_LEN}" \
  --kv-transfer-config "${KV_TRANSFER_CONFIG}" \
  --trust-remote-code

FROM nvidia/cuda:12.8.0-devel-ubuntu24.04 AS build

# SETUP: Install Build Dependencies
RUN apt-get update && apt-get install -y \

Claudia MCP server vs Archon OS vs GasTown (and better options)
You’re comparing three different “layers” of the agent stack:

1) Claudia (yuvalsuede/claudia) — task/sprint brain via MCP
Claudia is essentially a task/sprint/dependency/verification system exposed over MCP, so agents can create/claim/update tasks, manage sprints, and persist task context across sessions. It’s lightweight and CLI-first (Bun-based), and it’s great when you want structured work tracking without running a full RAG/knowledge platform. 

Best for: “make agents behave” (claiming tasks, dependencies, verification checklists) with minimal infrastructure.

2) Archon OS — full “knowledge + tasks + MCP server + UI” command center
Archon is closer to a full control plane: UI + API + agents service + MCP server, plus built-in knowledge ingestion (crawling, uploads), RAG/search, and task management designed explicitly to be shared across coding agents. It’s heavier than Claudia, but covers more of the “context engineering” surface area. 

Best for: one central “project brain” that combines knowledge base + tasks + agent tooling.

3) GasTown — multi-agent workspace manager for Claude Code at scale
GasTown is a multi-agent orchestration/workspace manager for running many Claude Code agents (20–30) with persistence via git-backed work tracking (“hooks”, “beads”, mailboxes, etc.). It’s not primarily about MCP aggregation or RAG; it’s about coordinating a swarm of coding agents reliably. It’s explicitly experimental. 

Best for: “I want a lot of coding agents running in parallel with durable state.”

So… which is “better”?
Depends what pain you’re trying to kill:

You need shared knowledge/RAG + tasks + UI + MCP → Archon

You need lightweight task/sprint state + verification gates → Claudia

You need to run 10–30 coding agents at once with durable work tracking → GasTown

They’re not direct substitutes; they’re different slices of the stack.

Other options that can beat all three (depending on your goal)
A) “Real” multi-agent application frameworks (not product UIs)
Microsoft AutoGen — agentic app framework (multi-agent messaging, runtimes, extensions) 

CrewAI — lean multi-agent orchestration (crews + flows, lots of community tooling) 

OpenHands — open source agent SDK + CLI + local GUI for coding agents 

These are “build your own agent system” primitives—often better when you care about productionization more than a single monolithic tool.

B) Workflow orchestration that’s actually durable (pairs well with agent stacks)
If you want “agents as workers” with retries, state, schedules, and visibility:

Conductor 

Temporal 

These often outperform agent-specific orchestrators once you start treating agent runs like real workflows.

C) MCP layer choices (proxy/aggregation)
Grafbase Nexus is strong as the “one MCP + LLM gateway” entrypoint (tool search, proxying, unified surface). 

If you want GitHub context, GitHub’s official MCP server is a solid default.

Summary of the Flow
Claude Code / N8N sends a prompt to http://localhost:8700 (Nexus).

Nexus evaluates the prompt. If the prompt mentions "files" or "docker", fuzzy search grabs only the relevant tools from docker-mcp-toolkit and hides the rest.

Nexus forwards the prompt + the filtered tools to LiteLLM.

LiteLLM routes the request to your RTX 5090, 3090Ti, or OpenRouter based on the model requested.

Clawdbot talks to borrowers, queries Mem0 for context (backed by Postgres/Qdrant), and uses LiteLLM/Nexus to generate the response.

Archon MCP is primarily a developer tool designed to run close to your filesystem so it can watch code and documentation, interact with local editors, and spawn local processes. screenshot

File‑watching and hot reload – Archon watches your local repo for new docs/tasks. Docker binds mount host files, but in‑container file‑watchers often miss events on Windows/WSL (especially with chokidar or fs.watch). As a result, changes to your repo may not be detected in real time.


Tool integration – Many Archon tools (e.g. code-analyzer, yarn/npm tasks) shell out to local binaries. In dev mode these expect to find your local Node installation and repo dependencies. GPU and network dependencies – Archon can call other MCP servers (e.g. your local Ollama or GPU LLMs) using hostnames and ports. In Docker Desktop the host.docker.internal mapping works, but you lose cross‑container introspection. Running Archon directly on the orchestrator machine avoids that complexity.


For production or a non‑interactive orchestrator, containerization is desirable: it isolates dependencies, ensures consistent versions, and simplifies deployment. The recommended pattern is therefore:


Dev: run Archon natively (or in WSL) alongside your codebase and editor, and mount volumes for memory persistence.


Prod: build a Docker image (as in infra/docker/archon/Dockerfile.archon) and run with a persistent volume for .archon and .claude directories. Use environment variables to point it at other MCP servers (Claude Flow, MetaMCP, etc.) for orchestration.

### Reserved Ranges

- **3000-3999**: Web UIs (Grafana 3000, Gitea 3000, Dify 3002, Archon 3737)

- **4000-4999**: APIs (Archon 4000)

- **5000-5999**: App services (n8n 5678)

- **6000-6999**: Databases (Qdrant 6333, FalkorDB/Redis 6379-6380)

- **8000-8999**: Inference & APIs (VLLM 8000, Zep 8000, Infisical 8080)

- **9000-9999**: Monitoring (Prometheus 9090, Node Exporter 9100, DCGM 9400)

- **11000-11999**: Ollama (11434)

- **12000-12999**: System services (MetaMCP 12008)


### Adding New Services

1. Choose port from reserved range

2. Add to relevant docker-compose.yml

3. Update PORT-MAPPING-REFERENCE.md (this file)

4. Create Infisical path entry: /machines/{pc}/SERVICE_PORT

5. Create Cloudflare route if external access needed

6. Update Tailscale ACL if specific network rules needed
