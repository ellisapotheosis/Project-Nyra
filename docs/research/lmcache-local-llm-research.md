## 1. LMCache Overview

### What is LMCache?

[LMCache](https://github.com/LMCache/LMCache) is the first and most efficient open-source **KV caching solution** for LLM inference engines. It extracts and stores Key-Value (KV) caches generated by modern LLM engines (vLLM and SGLang) out of GPU memory and shares them across engines and queries.

**Key Capabilities**:
- **Multi-tier Storage**: GPU memory → CPU RAM → Local Disk → S3/Remote storage
- **Cross-session Reuse**: KV caches persist beyond single requests and process restarts
- **Distributed Cache**: Share caches across multiple inference servers
- **Zero-copy Acceleration**: NIXL, GDS (GPU Direct Storage), and more

### How It Accelerates Inference

LMCache operates at the **chunk level** (typically 256 tokens):
1. **Identify** commonly repeated text spans (RAG context, conversation history, system prompts)
2. **Store** precomputed KV caches in multi-tier storage hierarchy
3. **Reuse** cached chunks instead of recomputing, skipping prefill computation

**Performance**: [By combining LMCache with vLLM](https://dineshr1493.medium.com/understanding-cache-lmcache-why-it-accelerates-llm-inference-2606cda43677), developers achieve **3-10x delay savings** and GPU cycle reduction in many LLM use cases, including multi-round QA and RAG.

### Supported Models

LMCache works with any model supported by vLLM or SGLang:
- Llama 2/3, Mistral, Mixtral, Qwen, DeepSeek
- All Hugging Face Transformers models
- Custom models following vLLM/SGLang APIs

### VRAM Savings

[LMCache offloads](https://docs.lmcache.ai/kv_cache/cpu_ram.html) infrequently used KV blocks from GPU memory:
- **GPU VRAM**: Hot cache for active inference
- **CPU RAM**: 5GB default (configurable up to 50GB+)
- **Local Disk**: Persistent storage, LRU eviction
- **Remote Storage**: Redis, S3, Mooncake for distributed access

**Example Configuration**:
```bash
# Default: 5GB CPU cache
LMCACHE_MAX_LOCAL_CPU_SIZE=5.0

# For 128GB RAM systems (like our GPU workers)
LMCACHE_MAX_LOCAL_CPU_SIZE=50.0
```

### Multi-Model Caching Strategies

LMCache supports **multiple concurrent models**:
1. **Per-model Cache Pools**: Separate cache namespaces per model
2. **Shared System Prompts**: Cache reusable system instructions once
3. **RAG Document Caching**: Cache retrieved document embeddings
4. **Conversation History**: Cache multi-turn dialogue context

### Cache Persistence Across Wake/Sleep Cycles

✅ **[LMCache persists caches across restarts](https://blog.lmcache.ai/2025-07-31-cachegen/)**:
- Disk and remote backends store caches persistently
- KV caches survive process restarts, system reboots, and wake/sleep cycles
- **Wake-on-LAN implication**: Caches remain valid after GPU workers wake from sleep
- **CacheGen compression**: Up to 3× smaller cache files for faster loading

**Recommendation for Wake-on-LAN Setup**:
1. Configure disk storage backend for persistence
2. Use Redis for cross-worker cache coordination
3. Pre-warm caches on wake with frequently-used prompts
4. Set generous cache expiration (24-48 hours)

### Wake-on-LAN Implications

**Cache Warming Strategy**:

1. **On Wake**: GPU worker boots, vLLM starts
2. **Pre-warm Cache**: Run common prompts to populate cache
3. **Redis Coordination**: Fetch shared cache entries from Redis
4. **Ready State**: Signal to load balancer that worker is ready

```python
# Pre-warm script for GPU workers on wake
import requests

COMMON_PROMPTS = [
    "Analyze this mortgage application...",
    "Calculate the monthly payment for...",
    "What are the eligibility requirements for..."
]

def prewarm_cache(vllm_url):
    for prompt in COMMON_PROMPTS:
        requests.post(f"{vllm_url}/v1/completions", json={
            "model": "mistralai/Mistral-7B-Instruct-v0.2",
            "prompt": prompt,
            "max_tokens": 50
        })
    print("Cache pre-warmed successfully")

if __name__ == "__main__":
    prewarm_cache("http://localhost:8001")
```

### Redis Cache Layer for Centralized Coordination

[LMCache supports Redis](https://redis.io/blog/get-faster-llm-inference-and-cheaper-responses-with-lmcache-and-redis/) as a remote backend for **distributed KV cache sharing**.

```

│ GPU Worker 1│◄───────►│   Redis     │◄───────►│ GPU Worker 2│
│ (RTX 3060)  │         │   Cluster   │         │ (RTX 3090Ti)│
└─────────────┘         └─────────────┘         └─────────────┘
                               ▲
                               │
                               ▼
                        ┌─────────────┐
                        │ GPU Worker 3│
                        │ (RTX 5090)  │
                        └─────────────┘
```

**Redis Configuration**:

```bash
# Install Redis
sudo apt install redis-server

# Configure LMCache with Redis backend
export LMCACHE_REMOTE_BACKEND=redis
export LMCACHE_REDIS_HOST=localhost
export LMCACHE_REDIS_PORT=6379
export LMCACHE_REDIS_DB=0

# Start vLLM with Redis backend
vllm serve mistralai/Mistral-7B-Instruct-v0.2 \
  --port 8001 \
  --kv-transfer-config '{
    "kv_connector": "LMCacheConnectorV1",
    "kv_role": "kv_both",
    "kv_remote_backend": "redis"
  }'
```

**Benefits**:
- **Cross-worker Cache Sharing**: All 3 GPU workers share the same cache
- **High Availability**: Cache survives individual worker restarts
- **Consistent Hit Rates**: Centralized cache improves hit rates across fleet

## 5. Distributed LLM Strategy

### Load Balancing Across 3 GPU Workers

[According to 2025 research](https://developers.redhat.com/articles/2025/11/21/introduction-distributed-inference-llm-d), modern LLM load balancing requires **cache-aware routing**.

#### Recommended Architecture: llm-d with LMCache

[**llm-d**](https://github.com/llm-d/llm-d) is a Kubernetes-native distributed inference stack with **LMCache-aware routing**:

- **Cache-Aware Routing**: Routes requests to workers with highest cache hit probability
- **Queue-Aware**: Considers queue depth on each worker
- **SLA-Aware**: Prioritizes latency-sensitive requests
- **Load-Aware**: Balances GPU utilization across workers

**Deployment**:

```yaml
# k3s deployment for llm-d router
apiVersion: v1
kind: Service
metadata:
  name: llm-router
spec:
  selector:
    app: llm-d-gateway
  ports:
    - protocol: TCP
      port: 8080
      targetPort: 8080
---
apiVersion: apps/v1
kind: Deployment
metadata:
  name: llm-d-gateway
spec:
  replicas: 1
  selector:
    matchLabels:
      app: llm-d-gateway
  template:
    metadata:
      labels:
        app: llm-d-gateway
    spec:
      containers:
      - name: envoy-gateway
        image: envoyproxy/envoy:v1.31
        ports:
        - containerPort: 8080
        volumeMounts:
        - name: envoy-config
          mountPath: /etc/envoy
      volumes:
      - name: envoy-config
        configMap:
          name: llm-d-config
```

**Redis-Based Shared Cache**:

```bash

# Persistence for cache durability
save 900 1
save 300 10
save 60 10000

# Network configuration
bind 0.0.0.0
protected-mode yes
requirepass your_secure_password_here

# Performance tuning

timeout 300

```

**vLLM Workers Configuration**:

```bash
# Worker 1 (RTX 3060) - vllm-worker-1.conf

```

**Cache Namespace Strategy**:
- Separate Redis databases per worker to avoid conflicts
- Shared system prompts in database 0 (all workers read)
- Model-specific caches in dedicated databases

## 6. Alternatives to LMCache

### Comparison Matrix

| Framework | KV Cache | Ollama Support | Performance | Ease of Setup | Best For |
|-----------|----------|----------------|-------------|---------------|----------|
| **vLLM** | ✅ PagedAttention | ❌ No | ⭐⭐⭐⭐⭐ | Medium | High throughput, production |
| **LMCache** | ✅ Multi-tier | ❌ No (vLLM/SGLang only) | ⭐⭐⭐⭐⭐ | Medium | Cache-heavy workloads |
| **SGLang** | ✅ RadixAttention | ❌ No | ⭐⭐⭐⭐ | Medium | Multi-turn conversations |
| **TGI** | ✅ Prefix caching | ❌ No | ⭐⭐⭐⭐ | Easy | Long prompts, HF ecosystem |
| **LocalAI** | ❌ Basic | ✅ Yes | ⭐⭐⭐ | Easy | Multimodal, OpenAI API compat |
| **Ollama** | ⚠️ Basic | ✅ Native | ⭐⭐⭐ | Very Easy | Development, quick prototyping |

### vLLM with PagedAttention

[**vLLM**](https://docs.vllm.ai/en/stable/design/paged_attention/) is the **de facto standard** for high-throughput LLM inference.

**Key Features**:
- [PagedAttention reduces memory waste to under 4%](https://medium.com/@bharathyelchuri/lmcache-vs-vllm-a-deep-technical-comparison-part-2-of-2-1fee48bb9db1)
- 2-4x throughput improvement over naive implementations
- Supports all major LLM architectures
- Production-ready with extensive optimizations

**When to Use**: Default choice for production deployments

**LMCache Integration**: [Minimal setup](https://docs.vllm.ai/en/latest/examples/others/lmcache/), add `--kv-transfer-config` flag

### SGLang

[**SGLang**](https://www.ersteiger.com/posts/vllm-vs-max/) introduces **RadixAttention** for prefix-based caching.

**Key Features**:
- [Up to 6.4× higher throughput with heavy prefix reuse](https://medium.com/@michael.hannecke/choosing-the-right-llm-inference-framework-a-practical-guide-acb3d1c40a5b)
- Optimized for multi-turn conversations and agent workflows
- Structured output support (JSON, regex constraints)

**When to Use**: Building agents, tool chains, or RAG systems with high prefix reuse

**Benchmark**: [Completed 500 prompts 16% faster than vLLM](https://www.ersteiger.com/posts/vllm-vs-max/) (Qwen3-8B)

### Text Generation Inference (TGI)

[**TGI**](https://huggingface.co/blog/tgi-multi-backend) by Hugging Face with multi-backend support (vLLM, TRT-LLM).

**Key Features**:
- [13x faster inference on long prompts](https://medium.com/@michael.hannecke/choosing-the-right-llm-inference-framework-a-practical-guide-acb3d1c40a5b) (v3.0 release)
- Seamless Hugging Face model hub integration
- Prefix caching for conversational workloads
- [vLLM backend integration in Q1 2025](https://huggingface.co/blog/tgi-multi-backend)

**When to Use**: Long conversational contexts + Hugging Face ecosystem

### LocalAI

[**LocalAI**](https://localai.io/) is an OpenAI-compatible, multimodal inference framework.

**Key Features**:
- [Model Context Protocol (MCP) support added October 2025](https://github.com/mudler/LocalAI)
- Multimodal: text, image, audio generation
- Automatic backend detection for NVIDIA/AMD/Intel GPUs
- [Distributed inference capabilities](https://localai.io/features/distribute/)

**When to Use**: Privacy-focused deployments, multimodal applications, drop-in OpenAI replacement

**Ollama Compatibility**: LocalAI can use Ollama models via GGUF format

### Phase 2: Distributed Deployment (2-4 Weeks)

**Goal**: Deploy vLLM + LMCache on all 3 GPU workers with Redis coordination

   - Implement health checks and failover

**Success Criteria**:
- All workers sharing cache via Redis
- Load balancer routing based on cache affinity
- 80%+ cache hit rate across fleet

### Phase 3: Production Optimization (4-8 Weeks)

**Goal**: Fine-tune for mortgage-specific workloads

1. **Cache Optimization**
   - Identify high-frequency prompts (mortgage calculations, document analysis)
   - Pre-warm caches with common patterns
   - Implement cache expiration policies

2. **Model Selection**
   - Benchmark different models for mortgage use cases
   - Quantize larger models (Q4/Q5) to fit on smaller GPUs
   - Deploy specialized models (finance, legal) per worker

3. **Wake-on-LAN Integration**
   - Implement pre-warming script on wake
   - Test cache persistence across sleep cycles
   - Optimize wake time to <30 seconds until ready

4. **Monitoring & Alerting**
   - Set up Prometheus + Grafana for metrics
   - Track cache hit rates, TTFT, TPOT, GPU utilization
   - Alert on performance degradation

**Success Criteria**:
- <500ms TTFT for cached queries
- >85% cache hit rate for common mortgage queries
- Automated wake-on-LAN with <30s readiness time

### Phase 4: Alternative Consideration (Optional)

If vLLM migration proves too complex, consider:

1. **LocalAI with Distributed Inference**
   - [LocalAI now supports distributed inference](https://localai.io/features/distribute/)
   - OpenAI API compatible (easier migration from Ollama)
   - Can use Ollama models via GGUF

2. **Hybrid Approach**
   - Ollama for development and quick testing
   - vLLM + LMCache for production inference


## Appendix B: Troubleshooting

### Common Issues

#### Issue: CUDA not available in WSL

**Symptoms**: `torch.cuda.is_available()` returns `False`

**Solutions**:
1. Ensure Windows NVIDIA driver is installed (>= 450.80.02)
2. Verify WSL2 (not WSL1): `wsl --list --verbose`
3. Do NOT install Linux NVIDIA drivers in WSL
4. Restart WSL: `wsl --shutdown` then reopen

#### Issue: vLLM OOM (Out of Memory)

**Symptoms**: `CUDA out of memory` errors

**Solutions**:
1. Reduce `--max-model-len` to limit context window
2. Increase CPU offload: `LMCACHE_MAX_LOCAL_CPU_SIZE=50.0`
3. Use quantized models (Q4/Q5/Q8)
4. Enable `--swap-space` for emergency disk swap

#### Issue: Low Cache Hit Rate

**Symptoms**: Cache hit rate <50%

**Solutions**:
1. Increase `LMCACHE_CHUNK_SIZE` (e.g., 512 instead of 256)
2. Pre-warm cache with common prompts
3. Check cache eviction policy (LRU by default)
4. Increase cache size (CPU/disk/Redis)

#### Issue: Redis Connection Timeout

**Symptoms**: `Error connecting to Redis` in vLLM logs

**Solutions**:
1. Verify Redis is running: `redis-cli ping`
2. Check firewall allows port 6379
3. Confirm `LMCACHE_REDIS_HOST` is correct
4. Test connection: `redis-cli -h HOST -p 6379 -a PASSWORD ping`
